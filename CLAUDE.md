# CLAUDE.md, boilerplate-symfony

Boilerplate personnel. Les conventions générales sont dans `~/.claude/CLAUDE.md` : ce fichier ne note que les choix propres au projet.

## Choix du projet

- **Type** : application Symfony rendue côté serveur. Twig produit tout le HTML, Stimulus et Turbo ne font qu'enrichir. Chaque page fonctionne sans JavaScript : le carrousel défile nativement et ses boutons sont masqués, les filtres du catalogue et le contact sont des formulaires classiques, la page Tâches remplace son squelette par un lien vers `/taches/liste`, qui rend alors la page complète (noindex, canonique vers `/taches`) au lieu du seul contenu du frame.
- **Architecture** : découpage par module puis par couche (`src/<Module>/<Couche>/`), selon l'architecture DDD commune aux boilerplates (D1 à D12). Modules métier : `Catalog` (forme complète : `Application/ShowCatalogPage` porte les décisions, catégorie inconnue ou page hors bornes renvoyées comme `null` que le contrôleur traduit en 404, échec du dépôt renvoyé comme page en erreur), `Blog`, `Contact`, `Content`, `Task` (forme réduite, sans couche Application : l'UI appelle directement le port du domaine, conformément à la règle « Application apparaît au premier cas d'utilisation qui décide »). Le contrôleur du catalogue ne garde que la normalisation de l'URL (redirection 301 vers la query string canonique), avant d'appeler le cas d'utilisation. `Site` porte les pages sans métier (accueil, légal, SEO, charte) et compose les modules. `Shared` est le socle sans métier (SEO, fil d'Ariane). Les couches portent leur nom DDD : `Domain` (sans framework), `Application`, `Infrastructure`, `UI` (contrôleurs minces, la couche de routage, et leurs formulaires et extensions Twig). Côté templates, `templates/shared/` remplace `core/` et `features/`.
- **Suivi des erreurs** : GlitchTip, par les SDK Sentry, activé seulement si `GLITCHTIP_DSN` est renseigné (`.env.local`, jamais versionné). Vide par défaut : aucun script, aucune requête. Côté PHP, `config/packages/sentry.yaml` : pas de donnée personnelle, pas de corps de requête, pas de traces, et les erreurs attendues (404, 405, 422, 503) ignorées. Le catalogue et le contact rendent leurs 503 et 422 sans lever d'exception, ils ne sont donc jamais remontés. Côté navigateur, `App\Shared\UI\Twig\ObservabilityExtension` n'expose la configuration aux templates que si elle existe. Le contrôleur Stimulus `glitchtip`, chargé à la demande, injecte le SDK après l'événement `load`, une seule fois par visite.
- **Mesure d'audience** : Matomo sans cookie, donc sans bandeau, activé seulement si `MATOMO_URL` et `MATOMO_SITE_ID` sont renseignés. Le contrôleur Stimulus `matomo`, chargé à la demande, pose `disableCookies` avant toute autre commande et charge `matomo.js` en asynchrone. Turbo remplace `<body>` à chaque navigation : chaque connexion du contrôleur compte une page vue, et `turbo:frame-load` compte aussi les navigations de frame qui changent l'URL (filtres du catalogue). La page « Données personnelles » ajoute un paragraphe « Mesure d'audience » seulement quand Matomo est activé. Le visiteur peut s'y opposer depuis la page Données personnelles (contrôleur `opposition-mesure`, fiche CNIL n° 17, section 16 de la spec commune) : le refus est gardé dans le stockage local (`assets/opposition_mesure.js`), lu par le contrôleur `matomo` avant toute commande et avant chaque page vue ; posé, aucune commande ni requête. La page n'affirme pas l'anonymisation de l'IP : réglage de l'instance, à activer avant la mise en ligne.
- **CSP** : `Content-Security-Policy-Report-Only` sur chaque réponse principale, par le paquet `kewinmarchand/csp` (dépôt GitHub déclaré en `repositories` de `composer.json`), utilisé seulement dans `src/Shared/Infrastructure/Security/` (`make arch-wrappers`). `SiteCsp::subscriber()` fabrique l'abonné du paquet (`config/services.yaml`) : directives par défaut, plus l'origine de `API_URL` (en `connect-src`, `img-src` et `media-src`, pour l'audio des articles), et celles de Matomo (script, appels, pixel) et de GlitchTip (envoi) quand leurs variables sont renseignées, lues à l'exécution (`%env()%`). Route `POST /api/csp-report` (`config/routes.yaml`, contrôleur du paquet) : une ligne par rapport sur la sortie standard du conteneur, 413 au-delà de 10 000 caractères, 400 sur un JSON invalide. Le `CMD` du `Dockerfile` écrit d'abord `[boilerplate-symfony] serveur démarré (<APP_ENV>)` (`docker/startup.php`) : PHP n'a pas de démarrage d'application propre. Couvert par `SiteCspTest`, `CspTest` et `tests/e2e/csp.e2e.ts`.
- **Tests d'observabilité** : `make test-e2e` relance l'image de production avec des valeurs factices (`OBSERVABILITY_ENV` dans `Makefile.qa.mk`) pour les tests marqués `@observabilite` : un faux GlitchTip local sur le port 3231, et un traceur Matomo factice intercepté sur `http://matomo.test/`. Aucune instance réelle n'est contactée. La CSP autorise les origines de Matomo et de GlitchTip quand leurs variables sont renseignées.
- **API commune** (spec commune, section 6) : `API_URL` choisit l'API, 8090 pour API Platform par défaut et 8091 pour Hono, sans autre changement de code. Un seul client, `api.client` (`config/packages/http_client.yaml`, `base_uri` et `Accept: application/json`), injecté par `#[Target('api.client')]` sur le paramètre `$apiClient` (Symfony 8.1 déprécie l'injection par le seul nom du paramètre). `App\Shared\Infrastructure\Http\ScenarioRelayHttpClient` le décore pour relayer `X-Scenario` depuis la requête en cours (ou `API_SCENARIO` à défaut), `ContentLocaleHttpClient` pour la langue (voir Langues). deptrac interdit le client HTTP hors des couches Infrastructure. Les API publient leur port sur `127.0.0.1` seulement : le service `php` est donc, comme `node`, sur le réseau de l'hôte (`network_mode: host`), et Caddy écoute sur `SERVER_ADDRESS` (`127.0.0.1:${HTTP_PORT}` en Compose, `:8080` par défaut dans l'image). Réseau de l'hôte réservé à Linux : sous Docker Desktop, il faut une API publiée sur toutes les interfaces et `API_URL=http://host.docker.internal:8090`.
- **Chemin de catégorie** : `App\Catalog\Domain\CategoryPath` est le seul point qui transforme le paramètre d'URL `plantes-interieur/feuillages` en catégorie (`resolve()`, `null` si un slug est inconnu ou si la profondeur dépasse 3). Le contrôleur en fait un 404, les templates en tirent le fil d'Ariane (`steps`), les liens enfants (`child`), le menu mobile et le sitemap (`catalog_paths()`).
- **Données** : aucune base, tout vient de l'API commune (`API_URL`). Chaque module traduit l'API dans `src/<Module>/Infrastructure/Http/` (traduction et dépôt HTTP), à l'aide de `App\Shared\Infrastructure\Http\ApiPayload`, qui vérifie la forme de chaque champ. Pas de génération de types en PHP : la traduction est le contrat. Le catalogue lit en parallèle `GET /api/products` (une page, tableau) et `GET /api/product-facets` (total et compteurs, mêmes filtres, sans tri ni page), ADR 0005 de l'API Platform : `CatalogTranslation::facetsQuery()` porte les filtres, `searchQuery()` les mêmes plus le tri et la page, et le nombre de pages se calcule depuis `totalItems` (au moins une). Attributs de produit configurables (section 23 de la spec commune, ADR 0007 de l'API Platform) : `attributes` des produits traduit en `ProductAttribute` (liste `product-attributes` de la fiche, absente si vide), `attributes` des facettes en `AttributeFacet` (une facette par attribut, `catalog-filter-attribute-<code>-<valeur>`), paramètre d'URL `attr-<code>` répété traduit en `attributes[<code>][]` ; `CatalogUrlState` ne vérifie que la forme du code et des valeurs (inconnus de lui avant l'appel, l'API ignore les inconnus) et garde leur ordre d'apparition, celui du formulaire. Erreurs réseau, 4xx et 5xx deviennent l'exception de chargement du module (états d'erreur avec relance). Le 422 du contact devient `ContactMessageRejectedException`, dont les violations s'affichent sous les champs du formulaire. Les dépôts en mémoire et `CatalogSearch` sont supprimés. En test, `MockHttpClient` sert des réponses réelles capturées sur l'API (`tests/Fixtures/api/`, `tests/Support/ApiMockResponseFactory.php`, `X-Scenario` compris) : `make qa` ne demande aucune API démarrée.
- **Carrousel de l'accueil** : produits « À la une » lus dans l'API par `CatalogRepository::featured()` (`GET /api/featured-products`), cochés dans l'admin des produits. `HomeController` les passe au partial agnostique `shared/carousel/_carousel.html.twig`, qui accepte un `href` facultatif par diapositive : le titre devient un lien étiré sur toute la diapositive (`carousel-slide-link`, `draggable="false"`). Après un glisser, Embla annule le clic (test e2e). L'e2e du clic vise le titre : sous Playwright, un clic ailleurs dans la diapositive n'ouvre pas la fiche (cause non identifiée), alors qu'il l'ouvre dans Chrome, vérifié à la main à 1280 × 720.
- **Fiche produit** (section 11 bis de la spec commune) : `Catalog/UI/ProductController` (`/produit/{slug}`) lit `CatalogRepository::findProduct()` (`GET /api/products/{slug}`, `CatalogTranslation::detail()`, `ProductDetail` avec le chemin de sa catégorie en `CategoryLink`) ; produit inconnu de l'API, 404 ; API en panne, 503 avec le titre de repli et `product-error`. `templates/catalog/product.html.twig` : fil d'Ariane Catalogue › catégories › produit, JSON-LD `Product` avec `Offer`, description construite, image de partage = plus grande variante WebP. Galerie (section 24 de la spec commune) quand `gallery` n'est pas vide (`product-gallery`) : image principale puis vignettes (`product-gallery-thumb`, image principale comprise, lazy, « Voir l’image N sur M », `aria-current="true"` sur l'affichée) ; sans JavaScript, des liens vers la plus grande variante, que le contrôleur Stimulus `product-gallery` (chargé à la demande) remplace par des boutons, et l'image affichée par celle d'un `<template>` au clic et aux flèches gauche et droite. `metaTitle` (option `meta_title` de `seo_page()`) et `metaDescription` remplacent le titre et la description construite quand ils sont saisis. Le sitemap liste les fiches (`productSlugs()`, pages de 48 lues jusqu'à une page incomplète). Les cartes du catalogue portent un lien étiré sur le nom (`catalog-product-link`) avec `data-turbo-frame="_top"` : la liste vit dans le cadre Turbo `catalog-results`, et sans cet attribut la fiche se chargerait dans le cadre (« Content missing »).
- **Produits similaires** (section 11 bis) : `ProductController` lit `CatalogRepository::similar()` (`GET /api/products?category=…&itemsPerPage=9`, sans le produit affiché, 8 au plus, `SIMILAR_LIMIT`) et `templates/catalog/product.html.twig` les passe au carrousel commun (`product-similar`) après l'`<article>`. Liste vide ou `CatalogLoadException` : la section disparaît, la fiche reste servie en 200. La réponse est directement le tableau des produits. Fixture `products-monstera.json`.
- **Panier** (section 11 ter) : tenu dans le navigateur, sans API. Domaine pur dans `assets/cart.js` (`addItem`, `setQuantity`, `removeItem`, `lineIn`, `countItems`, `totalPrice`, plafond 99, `formatPrice`) : ligne `{id, slug, name, price, quantity, translations}` identifiée par le produit, `slug` et `name` dans la langue de l'ajout, `translations` (`{locale, slug, name}`) dans chaque langue du site, dont `lineIn()` choisit celle de la page à l'affichage (nom, lien, libellés de la ligne). `ProductController` les lit côté serveur sur la fiche (`findProduct()` dans chaque langue d'`alternates`, une langue en échec omise) : aucun appel sur un site monolingue ni sans vente. Stockage dans `assets/cart_storage.js` (`localStorage` clé `panier`, lecture validée, ligne de l'ancien format relue avec son slug pour identifiant et sans traductions, mémoire de repli si l'écriture échoue, événement `panier:change` dans l'onglet et `storage` entre onglets), testés par `tests/js`. Trois contrôleurs Stimulus chargés à la demande : `cart-link` (compteur du header), `add-to-cart` (bouton de la fiche, cloné depuis un `<template>` au connect : absent sans JavaScript, sans doublon sur une page restaurée du cache de Turbo) et `cart` (page, lignes reconstruites seulement quand la liste des produits change, pour garder le focus du champ de quantité). `Cart/UI/CartController` (`/panier`, couche `CartUI` de deptrac) rend `templates/cart/index.html.twig` : `<h1>`, fil d'Ariane, `<noscript>` et gabarits, `noindex`, hors du sitemap. Le socle ne connaît pas le panier : `base.html.twig` passe `cart/_cart_link.html.twig` à l'en-tête (`cart_link`), et `ProductController` passe le gabarit `cart/_add_to_cart.html.twig` à la fiche (`purchase`). Nom accessible du lien composé du texte visible et de compléments `bui-visually-hidden` (axe refuse un `aria-label` qui ne contient pas le texte affiché). Playwright n'affiche pas les `<noscript>` sans JavaScript : l'e2e lit le message dans le HTML servi.
- **Pages légales** (ADR 0001 de l'API Platform) : lues dans l'API par le module `Content` (`GET /api/legal_pages/{slug}`), administrées dans son `/admin`. Les images des produits et des articles viennent de l'API (ADR 0002 de l'API Platform) : `ApiPayload::image()` lit l'objet `image` du contrat en `App\Shared\Domain\Image` (ou `null`), posé par `templates/shared/ui/_picture.html.twig` (paramètre `image`) ou directement dans la carte produit, et aucune image n'est rendue pour `null` (fond neutre pour la carte produit). Image de l'API en échec (section 28) : `bui-picture` sur son `<picture>` (le partial le pose pour le paramètre `image` seulement, hero et logo exclus) et `initImageFallback()` appelé une fois par `assets/app.js` (délégation sur le document, Turbo ne remplaçant que le `<body>`) : l'image garde sa place, invisible, sur le fond neutre de la bibliothèque (`tests/e2e/image-echec.e2e.ts`). Seuls le hero et le logo restent dans `assets/images/` (paramètres `name` et `widths` du même partial). La CSP autorise l'origine de `API_URL` en `img-src`. L'accueil affiche une alerte (`home-carousel-error`, page en 200 comme le blog) si l'API ne répond pas, et retire la section sans produit à la une. Les trois pages légales passent par `LegalController::renderLegalPage()` et le partial `templates/legal/_page_content.html.twig` : titre, introduction et sections de l'API (`legal-section`), page inconnue de l'API en 404, API en panne en 503 avec le titre de repli et `legal-error`. Le HTML vient de l'API, qui échappe le HTML saisi et retire les liens `javascript:` et `data:` : il est injecté par `|raw`, sans autre filtrage (décision de Kewin), et stylé par `.legal-html` dans `app.css` (listes, liens comme `bui-link`). Restent dans le front : la section « Mesure d'audience » et l'opposition (Matomo), et l'état de conformité du lien du pied de page (`site.accessibility`, `accessibility_compliance()`). Le h1 suit l'API, le `<title>` et la description restent ceux de `seo_page()`.
- **Fiche article** (section 2 bis de la spec commune) : `Site/UI/ArticleController` (`/blog/{slug}`) lit `ArticleRepository::find()` (`GET /api/articles/{slug}`, `ArticleTranslation::detail()`) ; article inconnu de l'API, 404 ; API en panne, 503 avec le titre de repli et `article-error`. `templates/blog/article.html.twig` : `seo_page()` reçoit `published_time` (`og:type` article) et `image` (plus grande variante WebP de l'article), options ajoutées à `SeoPageFactory`, et le JSON-LD `BlogPosting` ; fil d'Ariane Accueil › Blog › titre, lien de retour « Tous les articles » vers `/blog`. Rubrique et format sous le titre (`article-section`, `article-format`), lecteur `<audio controls preload="none">` (`article-audio`) avec la durée (`ArticleAudio::readableDuration()`) et l'intervenant, absent sans audio (section 25) ; `metaTitle` et `metaDescription` comme pour les produits. Le texte en HTML reprend `.legal-html`. Le sitemap (`SeoController`) liste les fiches, sans elles si l'API ne répond pas ; les cartes de l'accueil portent un lien étiré sur le titre.
- **Liste des articles** (section 2 ter) : `ArticleController::list()` (`/blog`) lit `ArticleRepository::findLatest(\PHP_INT_MAX)`, comme le sitemap ; API en panne, 503 avec relance (`blog-retry`). Carte commune à l'accueil et au blog, `templates/blog/_card.html.twig` (testid en paramètre, classe `article-card` du lien étiré, niveau du titre en paramètre : `h2` sur `/blog`, `h3` sous le `<h2>` de section de l'accueil), rubrique en sur-titre (`article-section`). Filtre par rubrique : `<nav aria-label="Rubriques">` en puces (`blog-section-link`, l'active en `aria-current="page"`), paramètre `rubrique` traduit en `section` par `findLatest()`, rubriques lues par `ArticleRepository::sections()` (`GET /api/article-sections`) ; aucune rubrique ou API des rubriques en panne, pas de filtre ; rubrique inconnue, liste vide (`blog-empty`). La canonique reste `/blog`.
- **Prix** : `App\Catalog\Domain\Price` en centimes, comme l'API. Les euros n'existent que dans l'URL (`prix_min`, `prix_max`, convertis par `CatalogUrlState`) et à l'affichage (`Price::format()`, filtre Twig `price`), plus de `* 100` caché dans le filtre.
- **Identité du site** (section 22 de la spec commune) : nom, accroche, logo, thème par défaut et couleurs lus dans `GET /api/site-identity` par le socle (`Shared\Domain\SiteIdentity`, `Shared\Infrastructure\Http\HttpSiteIdentityRepository`, une lecture par requête dans `Shared\UI\SiteIdentityProvider`, `site.yaml` en repli si l'API échoue), fonctions Twig `site_identity()` et `site_theme_style()` ; le bloc `<style>` des couleurs, rendu après les feuilles dans `<head>`, est autorisé par un nonce (attribut de requête `csp_style_nonce`, ajouté à `style-src` par `StyleNonceCspSubscriber`, et `<meta name="csp-nonce">` pour la feuille de la barre de progression de Turbo) ; `icon` (`SiteIcon`) remplace les favicons du site (`<link rel="icon">` 32 px, `apple-touch-icon` 180 px, icônes 192 et 512 du manifeste) et `shareImage` devient l'`og:image` par défaut (section 26) ; les cas avec logo, couleurs ou icône et image de partage passent par les scénarios `identite-logo`, `identite-couleurs` et `identite-icone`, la vente coupée par `sans-vente`, et les fiches avec métadonnées saisies par `metas` (mock PHP, et fausse API `tests/e2e/fixtures/fake-api.js` de la phase `@identite` de `make test-e2e`).
- **Vente en ligne** (section 27 de la spec commune) : `salesEnabled` de l'identité (`SiteIdentity::$salesEnabled`, `true` en repli), lu par `SiteIdentityProvider::salesEnabled()` dans les contrôleurs et `site_identity().salesEnabled` dans les templates. Coupée : aucun prix (cartes, diapositives, fiche, description construite, `offers` du JSON-LD `Product`), filtre de prix et tris par prix absents et leurs paramètres ignorés par `CatalogUrlState::fromQueryString(…, withPrices: false)` (redirection vers l'URL canonique, comme une valeur invalide), lien du panier absent (`base.html.twig` ne passe pas `cart_link`), `/panier` en 404, et `ProductController` passe `contact/_inquiry_link.html.twig` à la place du bouton d'ajout (`purchase`) : lien `product-inquiry` vers `/contact?produit=<slug>`. Le stockage `panier` n'est ni lu ni effacé. Le module `Contact` lit lui-même le produit (`InquiredProductRepository`, `GET /api/products/{slug}`, `null` si inconnu ou API en panne : formulaire simple), l'affiche (`contact-product`) et l'envoie en champ caché `product` ; la confirmation devient « Votre demande de renseignement a bien été envoyée. », et la redirection garde `produit`. Scénario `sans-vente` (fixture `site-identity-sans-vente`) dans le mock PHP et la fausse API de la phase `@identite` (`tests/e2e/vente.e2e.ts`).
- **Config du site** : un seul fichier, `config/packages/site.yaml` (nom, URL, audit d'accessibilité, navigation). La navigation alimente le menu, le sitemap, le plan du site et le fil d'Ariane.
- **SEO** : `App\Shared\UI\Seo\SeoPageFactory` est le seul point de construction des métadonnées. Chaque vue commence par `{% set seo = seo_page({...}) %}`, le layout ne fait qu'afficher. Les pages fixes passent leur clé (`page: 'blog'`, `'catalog'` à la racine du catalogue en page 1 seulement) : titre et description saisis dans l'admin (`GET /api/page-metas`, `Shared\Domain\PageMetaRepository`, section 26) remplacent ceux de la vue ; un titre saisi (page fixe, ou `meta_title` d'un produit ou d'un article) est servi tel quel, sans le nom du site ; vides ou API en panne, ceux de la vue. Le JSON-LD `Organization` de l'accueil prend `icon.png512` comme logo quand une icône est saisie, sinon `/icon-512.png`.
- **Erreurs** : classes `XxxException` du domaine avec un message métier en français. PHP réserve le suffixe `Error` aux erreurs du moteur, d'où l'écart de nommage avec le front.
- **Mode sombre** (section 20 de la spec commune) : `base.html.twig` sert `data-color-scheme` au thème par défaut de l'identité du site et `<meta name="color-scheme" content="light dark">` ; le script inline du mode renforcé applique aussi le choix mémorisé (`localStorage`, clé `color-scheme`, `auto` pour « système », `light` ou `dark`, absente pour le défaut du site) avant le premier rendu. Bascule : `templates/shared/layout/_color_scheme_toggle.html.twig`, balisage de référence du menu de boilerplates-ui à choix cochés, branché par le contrôleur `color-scheme`, chargé à la demande (`stimulusFetch: 'lazy'` : chargé d'emblée, il coûtait 150 ms de LCP et l'accueil tombait à 0,90 sur Lighthouse) (comportement vanilla `assets/boilerplates-ui/vanilla/menu.js`, initialisé une fois par document, Turbo ne remplaçant que le `<body>`) ; logique pure dans `assets/color_scheme.js` (testée par `tests/js`). Le contrôleur observe `data-a11y-mode` : le mode renforcé garde la page en clair, et le nom de la bascule signale le choix suspendu. Sans JavaScript, la bascule est masquée et la page suit le système. Couleurs : jetons seulement. En mode renforcé, le header resserre ses écarts pour tenir sur une ligne à 1280 px avec la bascule.
- **Icônes** : sprite SVG tiré de Lucide (spec commune, section 17). `icons.json` liste les noms utilisés. `make icons` génère `public/icons.svg` (un `<symbol>` par ligne, ordre alphabétique) et `src/Shared/UI/IconNames.php`, la liste des noms lue par la charte graphique. `make icons-check`, lancé par `make qa`, échoue si l'un des deux ne correspond plus à `icons.json`. Le générateur (`tools/icons.js`) tourne dans le service `node` (variable `NODE` du Makefile). Un seul partial affiche une icône : `templates/shared/ui/_icon.html.twig`, `<svg><use href="/icons.svg#nom">`, décorative par défaut, porteuse de sens avec `icon_label`. Le logo reste un SVG propre au projet, hors sprite.
- **CSS** : maison, dans `assets/styles/app.css`, sur les tokens de `@kewinmarchand/boilerplates-ui` (section 19 de la spec commune) : les variables du site (`--color-*`, `--font-size-*`, `--space-*`, rayons, conteneur, focus) sont des alias des variables `--bui-*`, qui portent aussi les valeurs du mode renforcé (tailles, couleurs, épaisseur du focus). Seules les valeurs propres au site restent écrites (`--color-surface-dark`, gouttières, voile du hero, surcharges du mode renforcé : texte secondaire et focus en noir). La bibliothèque est copiée dans `assets/boilerplates-ui/` (versionné) par `make ui` (`tools/ui.js`) depuis la dépendance de dev : la production n'a pas Node, et AssetMapper sert les fichiers tels quels. `boilerplates-ui.css` réunit tokens et composants en une seule feuille (chaque `@import` serait une requête bloquante de plus), chargée par `assets/app.js` avant `app.css` ; ses composants sont dans `@layer components`, la feuille du site, hors couche, garde la priorité. `make ui-check` (dans `make qa`) échoue si la copie ne correspond plus à la version installée. La charte lit les tokens dans `app.css` et résout les alias dans `boilerplates-ui.css` (`DesignTokens`). Composants : les templates écrivent le balisage de référence de la bibliothèque (`packages/css/reference/markup.ts`, classes `bui-*`) : bouton, icône (`_icon.html.twig` pose `bui-icon`), alerte (`shared/ui/_alert.html.twig`, action par `embed` dans le bloc `action`), champs Symfony par le thème `form/bui_layout.html.twig` (enregistré dans `twig.yaml` : libellé, aide, champ, erreur, et « (obligatoire) » écrit dans le libellé, RGAA 11.10, sans astérisque ni phrase générale), cases, boutons radio, interrupteur, fil d'Ariane, pagination (sans flèche inutile, page courante en lien `aria-current`), carte, badge, squelette, puces (`bui-chip` dans une `ul.bui-chip-list` : sous-catégories et filtres actifs retirables, la classe `chips` du site ne porte que la marge). ## Règles d'architecture et de lint propres au projet

Vérifiées par `make arch`, lancé par `make qa` et donc en CI :

- **deptrac** (`deptrac.yaml`, règle R12) : `Domain` ne dépend que de lui-même (ni framework, ni autre couche, ni autre module), y compris par un nom pleinement qualifié, plus `Shared\Domain` (valeurs du contrat sans dépendance : `Image`, `ImageSource`) pour `Catalog`, `Blog` et `Content`, qui exposent une image. `Application` dépend du `Domain` de son module. `Infrastructure` du `Domain` et de l'`Application` de son module et des frameworks. `UI` du `Domain` et de l'`Application` de son module, de `Shared` et des frameworks, et de l'`Infrastructure` seulement pour `Contact` et `Task`, qui n'ont pas de couche Application. `Site` peut dépendre du `Domain` et de l'`Application` des modules. `Shared` ne dépend que des frameworks. Les classes natives de PHP (`\DateTimeImmutable`, `\NumberFormatter`, exceptions) ne sont dans aucune couche et restent permises partout : elles ne sont pas un framework.
- **Wrappers** (règle R10, `grep`) : le sprite `icons.svg` n'est utilisé que dans `templates/shared/ui/_icon.html.twig` (hors `assets/vendor/` et de la copie `assets/boilerplates-ui/`, dont le toast et le tableau citent le sprite), Embla n'est importé que dans `assets/controllers/carousel_controller.js`, le paquet `kewinmarchand/csp` n'est utilisé que dans `src/Shared/Infrastructure/Security/` (le reste du projet passe par `SiteCsp`).
- **Auto-test** : `make arch-selftest` (`tools/arch-selftest.sh`) écrit 9 violations volontaires à leur emplacement réel (Domain vers Infrastructure, Domain vers Symfony par nom qualifié, module vers module, Shared vers module, UI du catalogue vers son Infrastructure, UI vers le client HTTP, le sprite utilisé hors du partial, Embla hors de son contrôleur, le paquet CSP hors de `Shared/Infrastructure/Security/`), exige que chacune soit citée, puis retire les fichiers. Une règle qu'aucun test ne viole peut être débranchée sans bruit.

Écarts assumés par rapport à l'arbre cible de l'architecture commune :

- `AccessibilityExtension` (fonction Twig `accessibility_compliance()`) vit dans `Site/Legal/`, pas dans `Shared/UI/Twig/` : elle lit la règle de conformité de `Site/Legal`, et `Shared` ne dépend ni des modules ni de `Site`.
- Les templates ne sont pas couverts par deptrac : les fonctions Twig sont globales, et l'en-tête partagé (`templates/shared/layout/_header.html.twig`) appelle `catalog_tree()` du module catalogue. C'est la composition faite par le layout du site, l'équivalent du menu passé en propriétés par la couche de routage des fronts JavaScript.
- Pas de règle de couches pour les contrôleurs Stimulus : l'architecture ne découpe pas `assets/controllers/` en modules, seule R10 (une bibliothèque tierce dans son seul wrapper) s'y applique.

ESLint (`eslint.config.js`) : seules `simple-import-sort/imports` et `simple-import-sort/exports`, en erreur, sur les fichiers `.js` (`assets/` hors copies tierces, `tools/`), corrigées par `make lint-js-fix`. Groupes : tiers (`node:`, paquets et noms de l'importmap), relatifs, puis effets de bord, que le plugin ne réordonne pas entre eux (les feuilles de style d'`app.js` gardent l'ordre de la cascade, vérifié). Pas de bibliothèque commune, de socle, de modules ni de vues à ranger côté JavaScript. Les tests Playwright en TypeScript n'y sont pas : il faudrait le parseur typescript-eslint.

PHP-CS-Fixer : `@Symfony` plus `declare_strict_types` (règle risquée, activée pour garantir `declare(strict_types=1)` partout).

## Pièges connus, réellement rencontrés

- **Image de dev** : `make up` reconstruit l'image de dev (`--build`, rapide grâce au cache). Le Caddyfile est copié dans l'image : une image non reconstruite sert une configuration périmée, par exemple une écoute sur `:8080` au lieu de `SERVER_ADDRESS`, et la passe e2e en dev échoue dès qu'un autre service occupe ce port sur la machine.

- **Port 8080 occupé** sur la machine de l'auteur (un serveur uvicorn), d'où 8095. Depuis, 8095 peut lui aussi être pris par un autre service de la machine : `make up HTTP_PORT=18095` (ou `make test-e2e HTTP_PORT=…`) déplace le site, Playwright suit la variable.
- **Clés répétées dans l'URL** : PHP écrase `?taille=S&taille=M` en ne gardant que la dernière valeur. `CatalogUrlState` lit la query string brute avec `HeaderUtils::parseQuery($query, true)`. Toute URL non canonique (ordre, valeurs vides ou invalides, défauts) est redirigée vers sa forme canonique.
- **Variable d'environnement réelle contre `.env.test`** : Compose injecte `SITE_URL`, qui gagne sur `.env.test`. `phpunit.dist.xml` la force avec `force="true"`.
- **WebTestCase redémarre le noyau entre deux requêtes** : un service remplacé par `getContainer()->set()` disparaît au second appel. `$client->disableReboot()` quand un test enchaîne GET puis POST.
- **Page 404 personnalisée invisible en test** : l'environnement `test` est en debug et affiche la page d'exception. Créer le client avec `['debug' => false]`.
- **`include` Twig transmet le contexte** : une variable `label` du template appelant ressortirait comme `aria-label` de l'icône. Le paramètre s'appelle `icon_label`.
- **Composants de la bibliothèque et règles du site** : les composants `bui-*` sont dans `@layer components`. Une règle de classe du site, hors couche, l'emporte quelle que soit sa spécificité : c'est voulu pour les surcharges (`.bui-button--outline[aria-current='page']`), mais une règle de mise en page qui vise un élément `bui-*` doit le faire exprès. Les bascules d'affichage préfixent toujours par `.header` ou `.js`.
- **Glisser au carrousel en e2e** : la souris de Playwright n'agit que dans le viewport, faire `scrollIntoViewIfNeeded()` avant de mesurer la piste. Les images portent `-webkit-user-drag: none` pour ne pas déclencher le glisser natif.
- **Pages qui n'existent qu'en dev** : `/_error/500` et `/charte-graphique` sont déclarées sous `when@dev` et `when@test`. Les e2e tournent sur l'image de production, puis `make test-e2e` relance le serveur de dev pour les tests marqués `@dev`. En fin de commande, c'est donc le serveur de dev qui tourne. Chaque cible démarre elle-même l'environnement qu'elle attend, dans sa recette et non en prérequis : dans une seule invocation (`make test-e2e test-a11y`), make ne rejoue pas un prérequis déjà satisfait, et `test-a11y` tomberait sur le serveur de dev, où la 404 est la page d'exception de debug.
- **Cache de test sans debug** : le test de la 404 crée un noyau `['debug' => false]`, dont le conteneur compilé n'est jamais revalidé. Après un renommage de classes, il référence des noms de classes périmés. `make test-unit` vide `var/cache/test` avant PHPUnit.
- **PHPStan et Symfony** : `typecheck` réchauffe le cache dev avant l'analyse, sinon `containerXmlPath` n'existe pas.
- **`localhost` contre `127.0.0.1`** : Chromium essaie `::1` d'abord, et un autre service de la machine peut répondre 200 avec un corps vide sur `[::1]:8095`. Caddy n'écoute que sur `127.0.0.1` : Playwright vise donc `http://127.0.0.1:…`. Lighthouse vise aussi `127.0.0.1:3230`, et `make metrics` lance son site avec `SITE_HOST=127.0.0.1` : l'URL canonique reste sur le même hôte que la page mesurée. Écouter aussi sur `::1` ne marcherait pas sur un poste où un autre service occupe déjà `[::1]` sur le même port.
- **Données de l'API dans les tests** : les textes attendus suivent l'API, avec l'apostrophe typographique (« Plantes d’intérieur »), 7 produits en mi-ombre, 9 en taille L, 1290 et 1590 centimes en tête du tri croissant de `plantes-interieur`. Les états d'erreur et de liste vide passent par `X-Scenario` (`page.setExtraHTTPHeaders`), relayé par le site vers l'API.
- **Charge machine** : avec plusieurs suites en parallèle sur le poste, Playwright dépasse ses délais. Il tourne sur 4 workers en local, 2 en CI.
- **Performance Lighthouse** : l'accueil et le catalogue tournent autour de 0,90 à 0,93. Lighthouse simule un réseau lent où tous les téléchargements simultanés se partagent la bande passante, et le serveur local est en HTTP/1.1 (6 connexions). Causes mesurées : les diapositives du carrousel hors écran se chargent malgré `loading="lazy"` (seuil de Chrome), d'où `content-visibility: auto` sur les diapositives (deux images de moins sur mobile). La première image produit de `feuillages` est l'illustration monstera, qui pèse 159 Ko en 800w, c'est le plancher actuel de cette page. Les mesures en place : préchargement de l'image LCP en tête du `<head>`, `fetchpriority="high"` sur la première image produit, pas de lazy sur les quatre premières, `sizes` alignés sur la mise en page réelle, contrôleurs du carrousel et du catalogue chargés à la demande. Lighthouse fait 3 runs et l'assertion porte sur la médiane, avec un seuil de 0,90 bloquant. La latence simulée des dépôts n'y est pour rien : mesurée à 0 ms, le score de l'accueil ne bouge pas.
- **`catalog_tree()` dans l'en-tête** : il est appelé sur chaque page rendue, pages d'erreur 404 et 500 comprises. Le dépôt HTTP ne fait qu'un appel par requête (arbre gardé en mémoire le temps de la requête), et `catalog_tree()` se replie sur la seule entrée « Catalogue » si l'API est indisponible, pour ne pas casser les pages d'erreur. Un cache entre les requêtes (cache pool Symfony, durée courte) reste à ajouter quand le trafic le justifiera.
- **`APP_SECRET` obligatoire** : `compose.yaml` l'exige (`${APP_SECRET:?}`), sans défaut connu. Compose interpole `compose.yaml` avant de fusionner l'override, donc un défaut dans `compose.override.yaml` ne suffit pas. Le Makefile génère un secret aléatoire à chaque invocation quand la variable n'est pas fournie. Sans `make`, exporter `APP_SECRET` avant `docker compose`.
- **Composer dans le conteneur** : `composer require --dev` a écrit des contraintes `*`, corrigées à la main en `^x.y`.
- **Lighthouse** : Chrome est lancé avec `--no-sandbox` (Ubuntu restreint les user namespaces). Les rapports restent en local dans `.lighthouseci/`.
